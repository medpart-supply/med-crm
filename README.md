# CRM медичної частини — розгортання на Render

Облік і рух медикаментів: аптека, підрозділи, заявки, рецепти, журнал операцій.

Застосунок — одна сторінка, весь стан зберігається на сервері, тому всі підрозділи
бачать одні й ті самі залишки з будь-якого пристрою.

---

## 1. Що потрібно

* акаунт GitHub (безкоштовний);
* акаунт Render (безкоштовний, картку на старті не питає);
* 15 хвилин.

## 2. Виклали код на GitHub

```bash
cd med-crm-render
git init
git add .
git commit -m "CRM медичної частини"
git branch -M main
git remote add origin https://github.com/ВАШ_ЛОГІН/med-crm.git
git push -u origin main
```

Репозиторій робіть **приватним** — у ньому лежить застосунок, яким користується частина.

## 3. Розгортання

### Спосіб А — через `render.yaml` (рекомендований)

1. Render → **New** → **Blueprint**.
2. Оберіть свій репозиторій.
3. Render прочитає `render.yaml` і запропонує створити вебсервіс + базу Postgres.
4. У полі **APP_PASSWORD** введіть спільний пароль доступу до сайту (придумайте свій, довгий).
5. **Apply**. Перший деплой триває 2–4 хвилини.

Адреса буде виду `https://med-crm.onrender.com`.

### Спосіб Б — вручну

1. **New → Postgres**: ім'я `med-crm-db`, регіон `Frankfurt`. Скопіюйте *Internal Database URL*.
2. **New → Web Service**: ваш репозиторій, Runtime `Node`, Region `Frankfurt`,
   Build Command `npm install`, Start Command `node server.js`.
3. **Environment** → додайте змінні:

| Змінна | Значення |
|---|---|
| `APP_PASSWORD` | спільний пароль входу на сайт |
| `SESSION_SECRET` | довгий випадковий рядок (Generate) |
| `DATABASE_URL` | Internal Database URL з кроку 1 |

4. **Create Web Service**.

## 4. Перший вхід

1. Відкрийте адресу сервісу — з'явиться сторінка з паролем частини (`APP_PASSWORD`).
2. Далі звичайний вхід у систему: підрозділ → обліковий запис → пароль.
   Стартовий пароль усіх підрозділів — `medchastyna`, система одразу вимагає його змінити.
3. Зайдіть як **Аптека**, відкрийте **Доступ** і заведіть облікові записи на реальних людей,
   а стандартні або вимкніть, або змініть їм паролі.

## 5. Скільки це коштує і що на безкоштовному тарифі

| | Free | Що варто взяти для щоденної роботи |
|---|---|---|
| Вебсервіс | засинає після 15 хв без запитів, прокидається ~хвилину | Starter — від $7/міс, не засинає |
| Postgres | 1 ГБ, **база видаляється через 30 днів** (плюс 14 днів на перехід) | платний план — від $6/міс |

Безкоштовного тарифу вистачить, щоб показати систему керівництву й попрацювати кілька тижнів.
Для постійного обліку переходьте на платні плани — інакше через місяць база зникне.
Про це Render попереджає листами заздалегідь.

**Диск замість бази не підійде**: на безкоштовному тарифі файлова система тимчасова —
усе, що записано у файл, зникає при кожному перезапуску або новому деплої.
Тому в конфігурації використано Postgres.

## 6. Резервні копії

У панелі зліва, поруч із профілем, є кнопка **«Копія бази»** — завантажує весь стан у JSON-файл.
Робіть це раз на тиждень і перед переходом на інший тариф.

Відновлення:

```bash
curl -b "med_gate=..." -X POST https://ВАШ-СЕРВІС.onrender.com/api/restore \
     -H "Content-Type: application/json" \
     --data @med-crm-backup-2026-08-04.json
```

Крім того, у самому застосунку є вивантаження залишків і журналу в Excel.

## 7. Оновлення застосунку

Файл `public/index.html` збирається з вихідного `med-crm.html`:

```bash
node build.js шлях/до/med-crm.html
git add public/index.html && git commit -m "оновлення" && git push
```

Render передеплоїть автоматично після `git push`.

## 8. Локальний запуск

```bash
npm install
APP_PASSWORD=test1234 npm run dev     # http://localhost:3000
```

Без `DATABASE_URL` стан пишеться у `./data/kv.json` — зручно для перевірки.

## 9. Що варто розуміти про безпеку

* Сайт закритий паролем частини (`APP_PASSWORD`), Render дає HTTPS автоматично.
* Паролі підрозділів зберігаються як SHA-256 із сіллю — у відкритому вигляді їх немає ніде.
* **Але** вся база (залишки, заявки, рецепти з ПІБ пацієнтів, хеші паролів) віддається
  браузеру одним файлом після проходження шлюзу. Тобто будь-хто, хто знає пароль частини
  й пароль будь-якого підрозділу, технічно бачить усі дані, а не лише свої.
* Рецепти містять персональні дані пацієнтів. Якщо система працюватиме не як внутрішній
  інструмент, а офіційно, потрібні окремі рішення: розмежування даних на рівні сервера,
  журнал доступу, шифрування, узгодження з вимогами щодо захисту персональних даних.
* Одночасне редагування: якщо двоє змінюють базу водночас, той, хто зберіг другим,
  отримає попередження і сторінка перезавантажиться з актуальними даними — нічого не
  затреться мовчки. Для кількох людей на невелику частину цього достатньо;
  для десятків одночасних користувачів потрібен повноцінний серверний API.
